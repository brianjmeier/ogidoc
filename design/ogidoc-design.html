Ogidoc · design draft

One file, two pens

You and the agent build software by editing the same pseudocode in place, taking turns. There is no chat. Turns stay small, like TDD baby steps: the agent builds what it understands underneath, test first and out of sight, and leaves anything it would have to assume as a question for you. Each line shows whether it is built, so when the pseudocode looks done, the software is done. Questions and proposals live inside the file. As pieces get settled, the agent moves them into named boxes beside the text, so the text stays short and holds only what's still open.

Notation

There is no syntax. Write any pseudocode.

A plan is as big or as small as you make it: one function, one feature, a whole app. The tool has no idea of a project. The agent copies whatever style you start in: lowercase prose, Python-ish, arrows, YAML. Nothing is reserved. The agent works out what each line is from what it says and where it sits, and the editor shows it. The file stays plain text that diffs in git and opens in any editor.

Turn loop

Turns, made of baby steps

Turns are strict: only one side holds the pen, and passing it is a keybind (⌘↵), so you never leave the keyboard. It isn't a TDD tool, but it has the rhythm of one. Each agent step is the smallest next piece: write a test from the line, watch it fail, make it pass, mark the line built, hand the pen back. Turns aren't a fixed size. Both sides decide how much a turn covers, and the defaults steer both toward small turns so nothing gets assumed. When the work is simple and clear, the agent may keep going until it reaches a gap.

Human turn
  • Edit anything, including the agent's lines. Open any box and edit inside it to disagree with the abstraction. Code doesn't change on your turn.
  • Ghost-text autocomplete whenever the agent judges it has something useful to suggest. There is no fixed rule.
  • Accept or reject the agent's last turn per hunk, or wholesale. Rejecting also reverts the code it built for those lines.
  • Pass the pen with ⌘↵. You can say nothing: the edits are the message. With no edits it just means “go on”.
Agent turn
  • Reads the file, the diff of your last turn, and the repo.
  • Thinks as much as it needs, in the background. Only its edits, questions and proposals reach the file.
  • Edits in place: adds detail, rewrites vague lines, asks questions, makes proposals, answers yours.
  • Moves settled pieces into named boxes whenever it decides to, so the text keeps only what's still open.
  • Works in baby steps: picks a line it understands, writes a failing test, makes it pass, refactors if needed. As many steps as the turn calls for. What kind of test a line needs comes from context; if that isn't enough, it asks.
  • Never guesses. It either stops at the first gap, or builds everything else that's clear and leaves the open decisions marked for your turn. Some turns build nothing.
  • Matches your notation and indentation.
  • Returns the pen. It may write a one-line note in the margin explaining a large rewrite.
Your rules
  • Turn size, whether to stop at the first gap or build around it, how strict the tests are: all of it lives in a set of skills and prompts.
  • They ship with defaults that favor small turns. You and the agent can change them per person or per codebase.
Underneath
  • When the agent builds, it changes real code on a branch, runs checks, and commits once per agent turn. Every turn can be undone on its own.
  • Plan and code are mapped to each other, and the margin mark is that mapping's status. Its size isn't fixed: a line, a block, or a box, whatever helps you and the agent understand each other. It varies with the person, the agent and the project.
  • Done is defined on the plan: no open question, no line waiting or needing a build, checks green. Then the code is done too.
  • If the hidden code is edited outside a turn, the agent flags the drift: a question on each affected line, which turns those lines red. It never quietly rewrites the plan or the code to match.
  • You see results by running the app. Reading the code is optional.
Prior art

Who is near this, and what is still open

Spec-as-source with hidden code is an active space, but every tool found imposes its own spec format, steers through chat, and regenerates code in one direction. A user-invented notation, in-file questions with turn-taking, and live per-line build status on free pseudocode did not turn up anywhere.

Worth borrowing

  • Ownership. Each box owns a set of files (CodeSpeak's managed files, Tessl's targets). Anything not owned is protected; the agent asks before touching it.
  • Stability. Don't touch code for unchanged lines, and patch rather than regenerate. Nondeterministic rewrites are the main complaint about every spec-as-source tool.
  • Line-to-code tracing. Keep a map from each plan line to the code and tests behind it, as literate-programming tools do. It drives the margin marks and lets a failing test turn the right line red.
  • Drift as a question. If the hidden code changes outside a turn, raise it as a question on the affected line instead of overwriting.
  • Small visible edits. Studies on AI co-writing found people lose track of large AI rewrites and keep more control with suggestions they have to act on. That supports strict turns and small proposals.

Decided so far
  • Strict turns. Passing the pen is a keybind.
  • No syntax. The agent recognizes questions, answers, proposals, examples, boxes and code names.
  • Turns have no fixed size. Defaults steer toward small ones; the rules are skills and prompts you can edit.
  • The agent decides when to autocomplete, when to make a box, and what kind of test a line needs. It works from context, or asks.
  • Text and boxes are always on screen together. Boxes keep the text short.
  • The size of the plan-to-code mapping varies with the person, agent and codebase.
  • Drift in the hidden code is flagged, never synced silently.
  • One commit per agent turn.
  • No project concept. A plan is any size.
  • Reasoning stays in the background. No traces in the UI.
